Rebuilt on the **actual theme from your Max Media site**, not an approximation of it.
I pulled `yherhr/Krause_Photography` from raw.githubusercontent and lifted the real
tokens, so this is the same design language rather than something adjacent to it.

Static HTML/CSS/JS. No build step, no dependencies, no framework.

Two things in there that aren't obvious:

**`.nojekyll`** — GitHub Pages runs Jekyll by default, and Jekyll ignores any file
starting with `_`. Your photographs are all `_DSC5307.jpg` and friends, so the moment
you localise them into `img/` they'd vanish with no error. Don't delete that file.

**Cache busting** — the css and js links carry a content hash
(`css/mkm.css?v=a1b2c3d4`), regenerated by `./tools/stamp-assets.sh`. HTML and
CSS deploy as separate files, so a browser holding the previous stylesheet will
apply it to newer markup and every rule added since renders unstyled. Run the
stamper after any change to `css/` or `js/`; the Actions workflow does it for you.

**`404.html`** — GitHub Pages serves it for a missing path at *any* depth, so neither
root-relative nor document-relative links are safe in it. It works out the site root
at runtime (`/<repo>/` on a project site, `/` on a custom domain) and sets its own
links from that.

## 3. Deploy

Full step-by-step in **[DEPLOY.md](DEPLOY.md)**. The short version: drop the contents
into the root of `yherhr/Max-Portfolio`, overwriting `index.html`, and leave
`services/` and `locations.html` alone so all 204 of those URLs stay exactly where
they are.

```bash
./tools/build-sitemap.sh    # walks the repo, picks up all 204 services pages
git add -A && git commit -m "Unify portfolio and photography as Max K Media" && git push
```

Changing the site's address later is one command — `./tools/set-site-url.sh
https://maxkmedia.com.au` rewrites canonical, og, JSON-LD, robots.txt and every
sitemap `<loc>`. Nothing else needs touching: every internal link and asset path is
depth-relative, so it resolves the same at a domain root, on a GitHub Pages sub-path,
and from `file://`.

## 4. Client site cards

Six now: Rokiovertime, CME Detailing, BX Realty, Rural Asset Protection,
Nutraviva and Krause Photography. `web.html` shows the first four — the client
web builds — and `index.html` shows all six.

The cards are **screenshots** in browser chrome, linking out to the live site.
Shopify sends `X-Frame-Options`, so an iframe was never going to work there, and
a blocked site still fires `load` on its error page — there's no reliable way to
detect it in JS and swap in a fallback. A screenshot always renders.

### Capturing them

```bash
npm i -D playwright && npx playwright install chromium
node tools/shots.mjs
```

**This works for every site, including the ones that block embedding.**
`X-Frame-Options` stops a page being put inside a frame; it doesn't stop a
browser visiting it and taking a picture. The script drives a real browser to
each URL, dismisses the usual cookie and newsletter popups so they don't get
baked in, and writes `img/work/<slug>.jpg` at 1440×900.

If you'd rather not install Playwright, drop your own images in `img/work/`
using exactly these filenames:

```
rokiovertime.jpg   cme-detailing.jpg   bx-realty.jpg
rural-asset-protection.jpg   nutraviva.jpg   krause-photography.jpg
```

Roughly 16:10 and at least 1440px wide. The cards crop from the top, so a
homepage's first screenful is what you want.

**Two are already captured.** `krause-photography.jpg` and
`rural-asset-protection.jpg` were rendered from your public GitHub repos —
neither live site is reachable from my sandbox, but both repos are, so I cloned
them and screenshotted the real pages locally. One caveat on the RAPS one: it's
a picture of **the repo's current build**, and production was last seen serving
a stale build via Cloudflare direct upload. If prod is still behind, that
screenshot shows something visitors can't yet see. Recapture after you redeploy.

**You can ship before either.** A card with no screenshot falls back to a
compact panel with the business name and domain — it's deliberately shorter than
a filled card so six empty ones don't read as a wall of nothing. A partial run
is safe for the same reason.

### The quote PDF

The builder has a **Download as PDF** button. It renders a proper one-page
document — your selection, the indicative range, how it's built up, and the
terms — then calls `window.print()`, so the customer saves it through the
browser's own print-to-PDF.

That's deliberate over a JS library: no dependency, no build step, nothing to
keep updated, and the output is a real PDF. The document lives in a `.qdoc`
element that's hidden on screen and revealed only to the printer, so nothing
about the page changes for someone who never clicks it.

While `confirmed: false`, the PDF carries the same **Worked example** notice as
the on-screen panel — you can't hand someone a document with placeholder rates
and no warning on it.

### Hourly rates and the callout

`js/pricing-data.js` now carries **your actual figures**: `hourly: 200` on the
automation tier, `hourly: 180` on the three web tiers. Those two numbers are
real; everything else in that file is still placeholder.

The callout is one number, not two — `calloutHours: 2.5`. Both the panel and the
PDF read:

> The standard 2.5-hour callout is included — waived because you subscribed.
> Off-plan the same callout starts at $500 before anyone looks at it. Work
> beyond it is billed at $200/hr.

The off-plan figure is computed (`hourly × calloutHours`), so it tracks the rate
automatically — $500 on automation, $450 on web. That comparison is the strongest
line in the whole builder: it puts a number on what not subscribing costs.

### If you ever want a genuinely live frame

`./tools/check-embeds.sh` reports which sites allow it. Anything it marks OK can
take `data-embed="live"` on that card's `.frame__view`; the iframe code is still
there, opt-in, and falls back to the screenshot if the frame never loads.

## 5. Adding media — the gallery is now data-driven

Nothing about the gallery is hardcoded any more. It reads `js/gallery-data.js`, which
is generated from your folders. Categories, chip labels, counts and masonry row spans
all come from that one file, so **adding photos never means editing HTML or
JavaScript.**

```
img/gallery/
  studio/     gym/       outdoor/
  family/     product/   business/     <- any folder becomes a chip
```

The workflow, start to finish:

```bash
./tools/optimise-images.sh ~/Pictures/studio-shoot-aug studio
./tools/build-thumbs.sh      # responsive variants
./tools/build-gallery.sh     # regenerate the manifest
./tools/stamp-assets.sh      # cache-bust, or browsers keep the old manifest
git add -A && git commit -m "Add August studio shoot" && git push
```

Drop a new folder in and it becomes a new filter chip with the right count, no other
changes. I tested that: adding a `business/` folder produced a `Business 2` chip on its
own.

### The 31 you sent: 368 MB → 7.9 MB → 1.91 MB delivered

Those were 4000×6000 camera originals averaging 12 MB each. Two stages:

**Stage 1 — optimise.** 2000px longest edge, quality 82, EXIF stripped:
`368 MB → 7.9 MB`.

**Stage 2 — responsive variants.** 7.9 MB was still the whole gallery at full
size on every device, which is what made it slow. Tiles display at roughly
470px on desktop and 190px on a phone, so a 2000px file was 4× oversampled on
desktop and 10× on mobile. `build-thumbs.sh` now generates 400 / 700 / 1000 /
1400px variants and the manifest emits a `srcset`, so the browser downloads the
size it actually needs:

| | before | after |
|---|---|---|
| Desktop 1440 @1x | 7.9 MB | **1.91 MB** |
| Desktop 1440 @2x retina | 7.9 MB | **3.53 MB** |
| Phone 390 @3x | 7.9 MB | **1.91 MB** |

Measured by loading the page and scrolling the entire 47-frame gallery. Because
tiles are lazy-loaded, the first screen is a fraction of that again. The
lightbox still pulls the full 2000px file — that's the one place the pixels get
used.

Two supporting changes made those numbers possible:

- The grid dropped to **one column below 400px**, which meant `sizes` resolved
  to `100vw` on a 390px phone, and a 3× screen then demanded ~1170px per tile.
  It's now one column only below 340px, so every real phone gets two columns
  and asks for ~516px.
- The width ladder is 400 / 700 / 1000 / 1400 rather than round numbers, chosen
  to land just above what the layout actually requests at 1×, 2× and 3×.

The whole flow when you add photos:

```bash
./tools/optimise-images.sh ~/Pictures/next-shoot apparel
./tools/build-thumbs.sh
./tools/build-gallery.sh
./tools/stamp-assets.sh
```

### Serving from a CDN

`img/gallery/cdn.txt` holds one line — a base URL every generated path is
prefixed with. Blank means serve locally from this repo. Set it with:

```bash
./tools/use-cdn.sh https://cdn.jsdelivr.net/gh/yherhr/mkm-media@main
./tools/use-cdn.sh --local        # to revert
```

That rewrites the manifest, re-stamps the asset links, and curl-checks a sample
of the URLs — a manifest full of 404s looks exactly like a broken gallery, so
it's worth catching at the point you change it.

**`mkm-media.zip` is the media repo, ready to push.** It mirrors the
`img/gallery/...` structure the URLs depend on, so don't flatten it. Create a
**public** repo (jsDelivr can't read private ones), push, then run the command
above.

**Be honest with yourself about why you'd do this, though.** The speed problem
was oversampling, and that's fixed regardless of where the files live. GitHub
Pages is already served through a CDN, so moving to jsDelivr won't make much
measurable difference on its own. What it does buy you is keeping ~17 MB of
binaries out of the site repo and out of its git history — that matters as the
library grows, and it's the reason to do it.

If you do: pin a tag rather than `@main`. jsDelivr caches `@main` for 12 hours,
so a replaced file can take that long to appear, whereas a tag is cached
forever and never surprises you.

### Images hosted elsewhere: img/gallery/remote.txt

`build-gallery.sh` regenerates the manifest from your folders, which would have
silently dropped the 16 photos still served from the Krause_Photography repo. So
it now also reads `img/gallery/remote.txt`:

```
url | category | label
```

Those 16 lines are in there. As you localise each one — copy the file into
`img/gallery/<category>/` — delete its line, or it'll show up twice.

Several of these are identifiable people. That's normal for a lookbook you shot

### The limits, for when the library keeps growing

| | Limit | Consequence |
|---|---|---|
| GitHub Pages published site | **1 GB hard** | Site stops publishing |
| GitHub Pages bandwidth | 100 GB/month soft | Throttling, then an email — not a bill |
| GitHub repo | 1 GB recommended, 100 MB per file hard | Push rejected over 100 MB |
| jsDelivr `/gh/` | **20 MB per file, 50 MB per repo** | 403 from the CDN |

Two things worth knowing:

- **jsDelivr won't carry a big library.** The 50 MB per-repo cap means the CDN
  you use today stops working once the media repo grows. Optimised media served
  straight from Pages is the simpler path, and Pages is already CDN-backed.
- **Don't reach for Git LFS.** GitHub Pages doesn't resolve LFS objects — it
  serves the pointer text file instead, so every image silently breaks. It looks
  like the obvious answer for large media and it's the one thing that definitely
  won't work here.

**If you do outgrow Pages** — video, or a library past a few hundred MB even
optimised — the move is object storage with a CDN in front, not a bigger repo.
Cloudflare R2 stands out because egress is free (10 GB storage free, then about
$0.015/GB/month); Bunny.net is similarly cheap and simpler to set up. You'd then
list the CDN URLs in `remote.txt`, which is exactly what that file is for.

**Video:** don't self-host it on this stack. A single 1080p minute is 30–60 MB
and one viral post would eat the bandwidth allowance. Unlisted YouTube or Vimeo,
embedded.

One more, since this is a business site: GitHub's Pages terms say it isn't for
sites *primarily* directed at facilitating commercial transactions. A marketing
and portfolio site is normal use; a storefront taking payments would not be.

## 6. On-call support and the quote builder

`support.html` is new: the on-call proposition, three tiers, and a configurator
that produces an indicative monthly figure.

### Set your rates before this goes live

**Every number in `js/pricing-data.js` is a placeholder.** They're structurally
sensible but they are not your rates, and I'm not going to invent numbers for
your business and let you ship them by accident. So while `confirmed: false`:

- the quote panel is headed **"Worked example"** and says the rates aren't final
- the browser console warns on load
- the deploy workflow raises a warning

Work through the file, then set `confirmed: true` and all three disappear. The
maths is:

```
monthly = (base x response x coverage + add-ons) x term
```

shown as a band of ±`rangePct`. Deleting an option removes it; deleting a whole
array removes that question — the UI and the calculation both adapt.

### On "tailored to the customer"

There are two readings of that and they're very different.

What I built is a **configurator**: the customer's own answers drive the number,
the breakdown is itemised in front of them, and two people making the same
choices see the same price.

What I didn't build is **per-visitor pricing** — showing different numbers to
different people based on inferred wealth, location, device or referrer. It's
unreliable technically (you're guessing from an IP and a user-agent), and in
Australia undisclosed personalised pricing runs at misleading conduct under the
Australian Consumer Law. It also tends to surface publicly at some point, and
a trades-and-services brand doesn't survive that well.

If what you meant was quoting each client individually — that's just normal
business, and it's what the "send this for an exact quote" button is for. The
builder gets them to a realistic ballpark so nobody wastes a call, and the email
arrives with their whole selection attached so your first reply can be a real
number instead of twenty questions.

### The automation tier

`domains` includes an industrial control system option. Publishing *rates* for
that is a bigger step than publishing capability — it reads as touting for work
in your employer's field at a specific price. Delete that one entry if you'd
rather not; everything else adapts.

### What it does

- Three tier cards, each prefilling the builder via `data-preset`
- Radio/checkbox groups generated from the config, keyboard navigable with
  arrow keys, `aria-live` on the result
- Itemised breakdown so the figure is never a black box
- "Send this" hands the entire selection to the enquiry email

### Mobile sweep — what it caught

**Inline styles beating media queries.** I'd set `style="grid-template-columns:repeat(4,…)"`
directly on three grids. Inline styles beat every stylesheet rule, so those grids never
collapsed on phones and long words spilled their tracks at 320px. Replaced with
`.chain--4` / `.chain--3` modifier classes that the responsive rules can actually
override, and added `overflow-wrap: anywhere` so no unbreakable string can widen a
track. (Same class of bug as the specificity trap in v1 — worth watching for.)

**Header overflow at 320px.** Brand + "BATHURST" tag + burger, all `nowrap`, exceeded a
320px viewport. The location tag now hides and the brand shrinks below 400px.

Re-verified at **320 / 390 / 430 / 768 / 1024 / 1280 / 1440 / 1920** on all four pages:
no element overflows, and `maxScrollX == 0` everywhere — the page genuinely cannot
scroll sideways, which is the test that matters rather than `scrollWidth`.
